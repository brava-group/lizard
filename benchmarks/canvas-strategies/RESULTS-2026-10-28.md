# Canvas prototype measurements — 2026-10-28

## Scope and method

These measurements used an Apple M1 with 16 GiB unified memory and a 5120 × 2160, 75 Hz display. The saved `benchmarks/canvas-strategies/fixtures/ultrawide-workbook.lizard` fixture has 3,887 nodes and 77 frames. Both programs used release builds. The prototype used a 5120 × 2160 offscreen canvas and a 5120 × 2100 Metal window; the current editor, with panels hidden, had a 5120 × 2020 physical-pixel canvas. The prototype generated camera positions inside its winit loop; the editor received the same 120 positions through its JSON control channel. This is a useful workload comparison, **not** a controlled display-latency or FPS comparison.

The camera trace contains 60 pan positions and 60 continuous zoom positions, scheduled at 75 Hz. `--trace-repeats=10` exercises 1,200 positions; `--trace-repeats=60` exercises 7,200. Times marked “first visual” stop when the frame is submitted to Metal, not when the display emits light. `present_call_ms` and queue completion are distinct timings; neither proves that pixels were displayed within that interval. Run-to-run values change with window focus and system load. Occluded Metal-window runs were discarded.

## Memory: the 471 MiB atlas

The 240-slot, fixed-size atlas is **471.3 MiB**, about **2.9%** of this Mac's 16 GiB. It is one GPU allocation, not the memory of the whole program. macOS's peak memory footprint includes considerably more than the process's maximum resident set size (RSS), so the footprint is the more conservative comparison for this unified-memory machine.

| Release process and workload | Atlas | Max RSS | Peak memory footprint |
| --- | ---: | ---: | ---: |
| GPU prototype, 10 traces, fidelity fallback for drop shadows | 471.3 MiB | 348 MiB | 1,104 MiB |
| GPU prototype, 10 traces, same fallback including preview | 471.3 MiB | 333 MiB | 1,093 MiB |
| GPU prototype, one verified trace, same fallback | 471.3 MiB | 407 MiB | 1,212 MiB |
| GPU prototype, 60 traces, same fallback | 471.3 MiB | 343 MiB | 1,091 MiB |
| GPU prototype, 10 traces, earlier GPU shadow path | 471.3 MiB | 359–362 MiB | 1,232–1,233 MiB |
| Current editor, extended comparison session including 10-trace runs, full app | Separate dynamic cache | 917 MiB | 1,469 MiB |

The current editor figures include its full interface and control server; the prototype is a separate renderer window. They are not identical application workloads. The prototype's fixed atlas did not grow with repeated pan and zoom. This Mac showed roughly half its memory available during the measured runs and no swap activity in the timed processes. The data does **not** justify imposing an arbitrary 256 MiB atlas target. A useful next check is an 8 GiB Mac or deliberate memory pressure with several documents open, then an adaptive budget if pressure or eviction costs warrant it.

## Effect fidelity

A controlled 512 × 512 scene compared the direct GPU output with the document renderer, using the fraction of pixels that differ by more than 4/255 in any RGBA channel. It is one representative scene per effect, not exhaustive parity.

| --- | ---: | --- |
| None | 0.072% | GPU |
| Drop shadow | **24.327%**; the shadow was visibly absent | CPU tile and preview fallback |
| Inner shadow | 2.943% | CPU fallback |
| Layer blur | 0.003% | GPU |
| Background blur | 0.072% | GPU |
| Noise | 13.096% | CPU fallback |
| Texture | 1.322% | CPU fallback |

With the drop-shadow tile fallback, the whole workbook differed from the CPU reference on **0.065%** of base-view pixels and **0.693%** of zoomed-view pixels; the earlier direct GPU path differed on **0.891%** and **0.914%**, respectively. Full tile preparation rose from roughly 5.3 s in clean ten-trace runs to 8.6–9.1 s with the fallback. This is a fidelity-versus-preparation-cost tradeoff, and the prototype still needs more effect combinations, masks, fonts, images, color profiles, and blend modes tested before it becomes the default renderer.

## Edit latency

The current editor's JSON command acknowledgement is not the same as a refined canvas frame. With the same fixture and a release build, five text-property edits refined in **93–167 ms**; creating a rectangle took **588 ms** to refine; adding a drop shadow took **175 ms**; four actual shadow radius edits refined in **149–169 ms**. The prototype's isolated GPU rectangle-fill patch took **25–35 ms** for four dirty tiles, plus **0.9–3.6 ms** to compose. That isolated patch does not include the editor UI, text shaping, effect invalidation, or a display flip. It cannot be used as an in-app edit-latency claim for the prototype.

## Readiness to make this the default canvas

### Follow-up: scheduling, capacity, and corpus checks

The 240-slot atlas was tested against smaller fixed budgets on the same three-trace warm-interaction workload. Capacity 160/200/220/230 produced 332/188/102/52 frames with missing base tiles out of 360; 240 produced **zero**. The 471.3 MiB atlas is therefore justified for this particular UltraWide trace. It is not a universal minimum for smaller displays. The full prototype's measured peak memory footprint varied from roughly 1.12 to 1.41 GiB across these runs; the atlas alone is not its process memory.

The worker previously held the GPU presentation mutex during CPU effect rasterization. Moving that rasterization outside the lock reduced one early-interaction run's median pan and zoom `present()` calls from 2.51/13.27 ms to 0.99/1.02 ms. A four-worker asynchronous CPU queue reduced full preparation in one run from 7.08 s (four-worker batches) to 3.87–4.36 s, depending on warm ordering and system load. These are short, unpaired runs; they establish that the worker structure matters, not a stable speedup percentage.

With four asynchronous workers and **after preparation**, a verified 120-position trace had no missing base tiles or stale detail. Its base and detail image differences from the CPU renderer were 0.065% and 0.693% of pixels above 4/255. Median/p95 `present()` call times were 3.16/6.75 ms for pan and 3.25/6.43 ms for zoom. The first visual was submitted at 0.94 s, complete preparation at 3.89 s, and peak memory footprint was 1.41 GiB. None of these are display-photon timestamps.

**Early interaction still fails the quality target.** When the trace starts after the initial visible base and detail tiles but while pan coverage is still preparing, 55 of 349 presented pan/zoom states in one run lacked at least one base tile, even after retaining completed tiles that had briefly moved outside the camera's prefetch region. Starting only after all base tiles hides that failure but delays the simulated interaction until preparation is complete. The current 512-pixel overview is visibly soft on a 5120-pixel canvas during that period. A full-width direct Vello render also hit its 4096-pixel intermediate-texture limit. Splitting the viewport into two 2560-pixel strips took 133 + 40 ms on the first direct-GPU render and still omitted unsupported effects. This is not a suitable sharp fallback yet.

The pixel corpus now covers 66 views from the example documents and the saved Lizard icon file. Eighteen views qualified for direct GPU rendering; their worst difference was 3.562% of pixels above 4/255 (1.403% average). The other 48 need a faithful fallback for at least one unsupported feature; their direct output was deliberately not treated as parity evidence. The icon contains both drop and inner shadows, so it remains on the CPU route. The complex workbook routes 99/160 planned base tiles and 59/78 detail tiles through that route.

The analytic rounded-rectangle shadow now renders on the GPU with a cutout for shadows hidden behind the shape. In a 72-case radius/spread/opacity/zoom sweep, the supported low-opacity subset's worst difference was 4.261% of pixels above 4/255. A clipped opaque frame with a child differed by 1.555%; an unclipped frame whose child stayed inside the rounded outline differed by 1.310%. Higher-opacity shadows diverged by as much as 39.254% in the direct experiment and remain on the CPU route. Only 20 of the workbook's 172 shadows currently qualify for the analytic path. The parity sweep is an executable gate, not a claim of support for arbitrary shadow shapes or blends.

These follow-up measurements strengthen the post-preparation case, while the early-pan failure, unsupported effects, real display timing, and in-editor edit/device tests still prevent making this the default renderer.

The prototype establishes a promising bounded GPU cache and, after preparation, covers the tested pan and zoom trace without missing base tiles. It does **not** yet prove default-renderer readiness. The outstanding evidence is:

1. Pixel parity over representative documents and effect combinations, including a faithful fast drop-shadow path rather than a costly CPU tile fallback.
2. A sharp and faithful initial preview, with measured time to first correct frame and early zoom behavior. The 28 stale-detail frames in the early trace exceed the desired 50 ms visual budget if they are visible to the user.
3. A single input and display-timestamp harness for both renderers, with the same canvas dimensions, to measure actual visible frame age and worst-case latency rather than `present()` or control-channel counters.
4. Integration behind a selectable editor backend, then real text, image, effect, pan, zoom, resize, document-switch, and device-loss tests. The isolated prototype cannot validate those editor interactions.
5. Sustained memory-pressure and lower-memory-device runs, plus native and WASM regression gates after integration.

The 471 MiB atlas is a reasonable measured starting point on this 16 GiB UltraWide Mac. The decision to change it should come from memory pressure, competing documents, and eviction costs, not a smaller round number.

### Reproducible random motion and cache eviction follow-up

The smooth sinusoidal trace did not expose a cache correctness bug. A new seeded `--trace=random` simulates 60 pointer-like pan samples followed by 60 quick, reversing scroll samples; the same 120 camera positions repeat so runs can be compared. At 75 Hz, three repeats request 360 positions. This is still synthetic input inside the prototype, not OS mouse and display timing.

The worker's `rendered` set originally rejected every later request for a tile it had ever produced. Once the bounded atlas evicted that tile, zoom could never restore it. A regression test now checks that a live request re-renders an evicted tile, while planned warm-up work remains deduplicated. In a three-repeat random run with a 240-slot atlas, this correction reduced stale zoom-detail frames from **155 to 49**. It did not eliminate them.

Warm-up region jobs are now submitted on demand, with live requests taking priority over planned work. In two alternating, three-repeat random comparisons, 2×2 regions finished preparation in 3.39/3.75 s versus 3.63/3.88 s for individual tiles, and peak memory footprint was 1.18 GiB versus 1.33/1.36 GiB. Presentation p95 varied across runs; these pairs do **not** establish a repeatable improvement in presentation latency. Both routes still had about 153–156 stale detail frames before the eviction fix. The compact region also passed a separate tile-pixel comparison against individual faithful renders.

An atlas with 255 total slots is the largest single texture-array allocation this GPU accepts when one slot is reserved for the preview: Metal reports a 256-layer limit. A 280-slot experiment previously aborted during texture creation; the prototype now checks the device limit and returns an error. The 255-slot atlas with 95 detail slots uses 500.6 MiB, about 3.1% of this 16 GiB machine. With the eviction fix, the random-trace sweep gave:

| 2×2 CPU regions in flight | Full preparation | Stale detail frames / ~180 zoom frames | Longest stale sequence | Peak process footprint |
| ---: | ---: | ---: | ---: | ---: |
| 1 | 5.33 s | 14 | 187 ms | 1.15 GiB |
| 2 | 3.88 s | **10** | **133 ms** | 1.23 GiB |
| 3 | 3.39 s | 20 | 267 ms | 1.21 GiB |
| 4 | 4.24 s | 23 | 307 ms | 1.21 GiB |

Each row is one release run with the window frontmost. The best observed setting still exceeded the requested 50 ms visible-quality limit; these are scheduled-frame streaks and do not claim display-photon duration. The first-preview interaction run at the best setting was worse: first visual submitted at 0.62 s, initial visible tiles at 3.01 s, and all warm tiles at 4.58 s. All 95 presented interaction frames had missing base tiles; the longest uninterrupted missing-base sequence was at least 1.27 s, and the longest stale-detail sequence was 0.68 s. The overview remained lower resolution while the detailed tiles were prepared. The prototype therefore remains a **no-go** as the default renderer, even though the post-preparation cache and memory results are promising.

A separate `--verify` run with the 255-slot/two-region configuration completed after an event-loop watchdog fix. Its random-trace base and zoom reference images differed on 2.113% and 1.229% of pixels by more than 4/255. The 120-position trace had zero missing base frames, but 11 stale-detail frames and a 147 ms longest stale sequence. The earlier run without the watchdog reached the image comparison and then waited indefinitely for a redraw; it was discarded rather than treated as a timing sample.

The next implementation gate is a sharp, effect-faithful path for uncovered areas during *early* pan and zoom. More atlas memory alone cannot solve the 1.27 s preview-phase gap. After that path exists, rerun the random and sinusoidal traces inside the actual editor with pointer events, display timestamps or frame capture, edit invalidation, device loss, native/WASM builds, and memory pressure. A fast `present()` call is insufficient evidence by itself.

### Sharp-preview feasibility probe

A full-resolution CPU geometry pass with effects omitted took 22.77 ms for the 5120 × 2160 workbook view, versus 503.15 ms for its full effect render, in one release run. Blending that sharp pass over a five-times-smaller effect preview reduced workbook pixels differing from the faithful image by more than 4/255 from 7.101% to 1.439%. The same method **failed** on the saved Lizard icon: a 1024 × 1024 geometry pass took 3.17 ms, but the hybrid raised the >4/255 difference from 5.723% to 11.968%. Visual inspection showed that opaque geometry covered the icon's inner shadow and softened surface treatment. This shortcut cannot be adopted as the fidelity solution. The probe and its PNG comparisons are in `geometry_overlay_parity.rs` and the ignored benchmark output directory.

The working-tree `cargo xtask ci` gate passed after fixing a timing-sensitive zoom-preview assertion: it had previously accepted an idle worker before the requested zoom's image reached the canvas. The benchmark package's release tests, controlled shadow and region parity probes, corpus parity run, and `cargo clippy --all-targets -- -D warnings` also passed. The benchmark package is separate from the shipping workspace, so this does not substitute for integration tests of a new editor backend.

### Follow-up: sharp geometry with a signed effect correction

The naive overlay above covered inner effects on the icon. A second prototype computes a **signed, premultiplied** correction from a faithful low-resolution render minus a geometry-only render at that same resolution. It adds this correction to the sharp geometry. Nodes with visible layer blur are excluded from the geometry-only pass so they do not appear as sharp polygons. The GPU version prepares one signed RGBA16Float correction texture with a compute pass; the presentation shader then samples the sharp geometry and this one correction texture. The alternative `--baked` applies the correction to the large geometry image in parallel on the CPU before GPU upload. Both are *approximate*: this technique cannot reproduce every high-frequency effect and is not a replacement for a faithful final render.

The macOS worker wakeup was changed to an event-loop proxy after a real shutdown deadlock between synchronous `request_redraw` and the main thread's GPU wait; the revised benchmark exits cleanly.

### Continued readiness work: finite coverage and live vector fallback

An early attempt to draw individual faithful tiles over the sharp full-window image exposed visible rectangular seams. The two paths differ at antialiased edges, so mixing them in one incomplete viewport is unacceptable. The streaming experiment now draws the sharp image until **all visible base and detail tiles** are present, then switches the whole viewport. A real screenshot of a moving, partially warmed viewport showed the seams before this change and a clean viewport afterward. It remains an experimental policy, since the switch itself can still change some edge pixels.

The first overscan benchmark knew every future camera position. `streaming_window` now defaults to a finite source around the first camera and reports how much of the trace it covers; `--oracle-source` reproduces the earlier comparison. With a 512-world-unit guard and a 1,200-state random trace, only **480/1,200** cameras fit the prepared source. Deferring all faithful tiles until interaction ended then made the 1,200-state presentation smooth (1,172 presented, pan/zoom p95 17.05/16.79 ms, no `present()` call over 50 ms), but it would leave 720 states without coverage. This is a decisive failure for that method on its own, despite its good timing.

The full 5120×2160 Vello geometry path, with effects disabled in Vello and supplied by a cached low-resolution correction, provides coverage outside a finite cache. Its low-resolution effect source was computed from the document's own bounds, rather than the trace. On the Apple M1, one serial 120-frame probe had a 13.23 ms median but a 66.04 ms p95 and 17 frames above 50 ms; it differed from the CPU renderer by about 2.0–2.6% of pixels above 4/255 and 0.37–0.50% above 16/255 at six sampled cameras. The serial probe includes a wait after every frame. The real Metal-window trace removes that wait:

The cache/live visual comparison now samples seven cameras, not just the initial position, and includes the faithful document renderer. With a 1,024-unit source, the original GPU-base effect residual changed **2.19–2.80%** of pixels above 4/255 at the cache/live handoff; the live path changed **2.01–2.61%** against the reference. GPU-only geometry differed from CPU geometry on **0.767%** of pixels above 4/255 at the first camera. Using the CPU geometry at the low effect resolution as the residual base (`--low-cpu-base`) reduced handoff difference to **0.96–1.39%** and live/reference difference to **0.60–0.92%** across the same seven cameras. Cache/reference remained **0.96–1.58%**. These changes improve fidelity, but do not establish pixel equivalence; high-frequency effects and antialiasing still differ.

The benchmark's main thread originally called `device.poll()` after every present. An optional 1 ms background poll loop (`--poll-background`) moves callback maintenance off that thread. Three sequential 1,200-state runs with a 1,024-unit guard, two-pass cached presentation, and the CPU low-resolution base gave **1,139, 1,124, and 1,130** presented states; `present()` p95 **16.99, 16.87, and 16.22 ms**; max **36.26, 40.00, and 28.92 ms**; queue-completion p95 **38.31, 39.91, and 45.61 ms**; and **8, 16, and 19** callbacks above 50 ms. None had a `present()` call above 50 ms. In one 512-unit run that actually used the live fallback for 648 frames, the same polling change gave 1,091/1,200 presented, `present()` p95/max **26.51/42.78 ms**, and queue-completion p95 **47.25 ms** with 38 callbacks above 50 ms. The live fallback remains too slow for the requested target, and the callback timings are not display-photon measurements.

Sampling the high-resolution cache with nearest-neighbor filtering was also tested at the same seven cameras. It reduced the cache/reference error above 4/255 from **0.96–1.58%** to **0.71–1.31%**, but increased the error above 16/255 from **0.39–0.58%** to **0.51–0.68%**. This trades small differences for larger edge artifacts, so linear filtering remains the default experiment.

These are separate renderer windows, not the editor. The 1,024-unit source is based only on the first camera, but the random trace is clamped to a finite area and happened to fit it. Other navigation must use the slower live fallback or prepare a new cache. The hybrid currently prepares synchronously before its trace (about 1.6 s); the measured standalone residual prepares in the background but has no arbitrary-pan coverage. Combining their startup paths inside the editor remains untested. A switch between the CPU-generated cache and live GPU path changed 2.793% of pixels above 4/255 and 0.756% above 16/255 at the same camera; a GPU-generated cache increased those to 3.257% and 0.906%. Side-by-side images look close at reduced size, but the transition needs a timed capture and a perceptual gate. The GPU-generated cache initially exceeded wgpu's requested 8192-pixel texture limit; it now renders in bounded horizontal bands, and the benchmark exits without that validation panic.

Pixel parity also depends strongly on camera phase. Individual faithful tiles at a fixed integer-aligned camera differed from the CPU viewport by 0.065% of pixels above 4/255; the random trace's fractional camera differed by 2.115% even **without** region grouping. Earlier attribution of that entire difference to grouped rendering was wrong. The 2×2 region route is still optional, but the current evidence does not isolate its contribution from camera resampling. This must be resolved before using a pixel threshold as a default-renderer gate.

**Readiness decision remains no-go.** The new cache plus live fallback is the best coverage candidate measured here, but the worst-case frame, route transition, icon/effect fidelity, edit invalidation, memory pressure, actual display timing, resize and device-loss behavior, and native/WASM integration have not passed. The 1.8 GiB RSS is an observation on this 16 GiB Mac, not an arbitrary rejection threshold. The benchmark package's release tests and all-target clippy gate passed earlier in this experiment; the root `cargo xtask ci` gate passed after a temporary-directory collision in one engine test was fixed. In-editor validation is still separate.

### Bounded geometry atlas and swapchain phase measurements

A further standalone experiment keeps 1024-pixel geometry tiles in a bounded Metal atlas, prepares tiles on two CPU workers, and uploads them on one dedicated worker. A low-resolution, document-wide signed effect residual is composed over the sharp tiles. The first static visual is submitted at roughly 1.3–1.6 s and initial two-tile overscan becomes resident at roughly 1.7–2.1 s. These are **not** instant-open times. The atlas can draw only when all visible tiles are resident; otherwise it falls back to live Vello geometry. A prewarm flag makes the trace wait for initial atlas coverage, so it does not measure background readiness under immediate user interaction.

The first 160-slot, three-tile-margin run presented 1,172/1,200 requested states, with `present()` p95/max of 16.19/29.19 ms and five queue callbacks above 50 ms. Its measured peak process footprint was 3,248,035,712 bytes (3.03 GiB). Reducing to 96 slots and a two-tile initial margin lowered one peak footprint to 2,809,566,848 bytes (2.62 GiB). The latter held 77 tiles initially and 93 by the end of the bounded trace. These are whole-process footprints, not atlas-only allocations. The memory change is confounded with the different margin and run conditions; it is a capacity comparison, not a precise 438 MB causal saving.

Five sequential 96-slot, two-margin, 500 ms idle-redraw runs of the same 1,200-state trace yielded 1,161–1,167 presented states, `present()` p95 16.35–17.17 ms, max 30.97–40.40 ms, and 3–11 queue callbacks above 50 ms. None had a `present()` call above 50 ms. Separate 1-second, 2-second, and 4-second idle-redraw intervals also avoided a >50 ms `present()` call in two, two, and three runs, respectively. Earlier single runs without the extra static atlas presentation produced acquisition stalls of roughly 79–211 ms even after every trace tile had been prepared, so the apparent improvement is promising but the mechanism and long-run reliability remain unproven. Periodic redraw has an idle power cost that has not been measured.

An excursion trace pans roughly 1,700 world units outside the initial cache and reverses while zooming. With 96 slots and a two-tile margin, two 1,200-state runs presented 1,125 and 1,130 states; 10 and 9 of those used the live fallback. `present()` p95 was 26.37 and 26.49 ms, with 40 and 30 queue callbacks above 50 ms. The phase instrument shows that the expensive portion is drawable acquisition: in the second excursion run, acquisition p95 was 26.09 ms while tile scheduling, GPU draw submission, and present call were 0.04, 0.60, and 0.08 ms. On the bounded trace, acquisition p95 was 14.18 ms while GPU draw submission was 0.62 ms. Upload-limit probes on the excursion trace were variable: limit 1 presented 1,099 states and used 66 live frames; limit 2 presented 1,125 with 10 live frames; limit 4 presented 1,148 with six live frames. Their acquisition p95 values were 26.28, 26.21, and 16.24 ms. One run per setting cannot establish that increasing the limit caused the last improvement.

At seven sampled cameras, atlas/reference disagreement was 0.927–1.439% of pixels above 4/255 and 0.453–0.577% above 16/255. This is an improvement in sharp coverage, not pixel parity; the effect correction can still differ from the faithful renderer. The saved first-camera actual/reference PNGs are in ignored `target/canvas-strategies/atlas-{actual,reference}.png`. The bounded atlas has not been connected to document edit invalidation, resize, document switching, color profile handling, the editor's egui WGPU callback, device loss, or the WASM fallback. The excursion run still coalesced 70–75 camera requests, and callback completion is not a display-photon timestamp. **It is still unsafe to make this standalone route the default editor renderer.**

### Faithful atlas, detail tiers, and edit invalidation

The atlas can now retain complete CPU-rendered effects in its tiles (`--atlas-faithful`) instead of compositing a low-resolution effect residual. Initial coverage of the complex workbook took roughly 4.4–4.8 s in the measured runs. A 1,200-state motion run presented 1,172 states, with a 15.72 ms p95 `present()` call and a 37.94 ms maximum, but 18 GPU queue-completion callbacks exceeded 50 ms. Peak process footprint was 2.56 GiB. These are separate-window measurements, not editor or display-photon timings.

The new detail tiers keep an atlas tile's raster scale at or above camera scale. On the 2×–8× zoom trace, 240 slots with no motion overscan presented 1,150–1,156 of 1,200 requested states across three runs; 1,048–1,061 used the sharp atlas and 95–107 used the live-vector fallback. `present()` p95 was 15.65–16.45 ms, the worst call 40.21–41.07 ms, and 25–48 queue callbacks exceeded 50 ms. Peak process footprint was about 3.45–3.53 GiB. The first zoom cycle still relied heavily on the fallback; later cycles used the atlas almost entirely. Reducing capacity to 192 or 224 slots increased live fallback and produced p95 calls around 26 ms. Static and dynamic zoom-tier prefetch increased contention in the tested traces, so the dynamic policy was removed. Seven high-zoom atlas views differed from the CPU reference on 0.452–1.439% of pixels above 4/255; visually inspected saved 8× views stayed sharp. The live-vector fallback differed on 0.402–0.924% of pixels above 4/255 at five cameras, but a live-only 120-state run presented only 75 states.

Document generation IDs prevent old render jobs from reinstating stale tiles after an edit. On the saved Lizard icon, a complete invalidation took 480–488 ms to restore coverage; explicitly invalidating only the affected tiles took 325–328 ms. A first per-tile pixel patch took 78–80 ms. Rendering one shared patch per detail tier and using dedicated edit workers brought ten explicit-damage runs to 36–41 ms on the icon (four atlas tiles) and 21–22 ms on the complex workbook (two tiles). The edited icon and workbook differed from their CPU references on 0.480% and 1.855% of pixels above 4/255, respectively, close to their pre-edit atlas differences of 0.484% and 1.842%. These measurements include the CPU patch render and WGPU upload submission, but not display presentation.

Effect-aware automatic damage now uses the retained renderer's change analysis and safely falls back to full invalidation if it cannot establish a local patch. Ten automatic-damage runs took 36–47 ms on the icon and 43–46 ms on the workbook for a topmost simple rectangle addition; pixel comparisons were unchanged. For the icon's `New Icon` drop shadow (radius 10, offset 15, opacity 35%), toggling visibility touched all 16 visible tiles and still took about 180–200 ms even after grouping patches into a 3,072-pixel region; 1,024-pixel grouping took about 380–410 ms. This effect edit **fails** the desired under-50-ms responsiveness gate. An effect edit in the workbook took 42 ms, showing that the cost depends on affected area and effect complexity.

**Readiness remains no-go.** The standalone prototype still needs editor integration, actual display timestamps, responsive edits of large effects, memory-pressure and multiple-document tests, document switching, resize, device-loss handling, and a native/WASM fallback. The sharp atlas improved pan and zoom coverage on these traces, but these results do not prove it safe as the default renderer.

### Editor integration probe (feature gated)

The shared atlas and compositor now live in `lizard-canvas-gpu`, and an opt-in bridge can paint its native WGPU texture inside the editor. The ordinary CPU canvas remains visible until every tile in the current viewport is resident. The default build does not enable the bridge. The first editor run exposed a real WGPU lock inversion: a background `write_texture` and the window thread's `submit` blocked each other. The editor bridge now installs tiles on the window thread; the standalone atlas still supports its background-upload path. The owner-thread variant produced the same **0.484%** icon difference above 4/255 as the earlier atlas, with 16/16 tiles resident after **999 ms** in a standalone parity command run during CI compilation. That time is not a clean startup baseline.

In a 1440×900-point editor window showing the saved icon, the first full atlas view appeared after **1.03–1.16 s** in two runs before adaptive capacity, while the existing canvas supplied the initial image. A 40-pan/40-zoom control-channel trace returned pan p95/max **16.27/21.88 ms** and zoom **5.93/9.15 ms**, with no control response above 50 ms. These are command-response times, not frame presentation or display latency. A second 60-pan/60-zoom trace ran while the CI build competed for resources, so its response times are not comparable; its camera coverage log showed **39/40** complete views after pan and **61/80** at the start of zoom. The incomplete views use the editor's existing fallback, so the no-blur goal is not met. macOS placed the second instance in another Space; its window screenshot was blank, so in-editor visual inspection remains unverified.

The original 240-slot editor bridge showed a **2.4 GiB** footprint and **2.7 GiB** peak in one icon session, while the standalone atlas's fixed allocation was 471 MiB. The editor bridge now chooses capacity from the viewport, retaining 240 slots for UltraWide widths. A 1266×1720-pixel canvas selected **144 slots**; its measured footprint was **1.3 GiB**, peak **2.0 GiB** during concurrent CI compilation. These are not controlled paired memory runs and should not be interpreted as a precise saving. A quiet, paired editor comparison is still needed. A later visible-window capture did show the full icon; the earlier blank capture was caused by the hidden window, not a proven rendering failure. The visible GPU and CPU captures were at different zooms and cannot be treated as pixel parity.

### Follow-up: sparse atlas and idle zoom preparation

The first in-editor atlas used a fixed 2.4× raster base even when the camera was far below 1×. In the saved icon at a 4300×2020-pixel UltraWide viewport, this required 91 resident tiles at the initial 0.5× camera and covered only **32/60** pan positions with 240 slots. Changing the raster tiers to start at 0.3× with at least 1.5× sampling, then treating tiles outside the document's conservative paint bounds as clear, reduced the initial resident count to **9** and covered **60/60** pan positions. The sparse-tile rule has a unit regression test. It needs more corpus coverage before the experimental path can be made default.

At 1024×1024, the updated icon atlas differed from the document renderer on **0.070%, 0.249%, 0.484%, 0.401%, 0.188%, and 0.109%** of pixels above 4/255 at camera scales 0.15, 0.5, 1, 2, 4, and 8 respectively. This measures one icon, not all features or a full UltraWide frame. A damage-based edit invalidation returned in **0.30 ms** for a rectangle edit and **0.32–0.36 ms** for four drop-shadow visibility toggles, preserving the resulting pixels within 0.481–0.484% of the reference. The faithful replacement tiles for those shadow toggles took another **242–479 ms** to become ready; invalidation time must not be presented as visual edit latency.

Guarded idle preparation keeps the current view and a one-tile pan margin resident and uses a separate, bounded worker queue. On the 1266×1720 icon trace with the earlier raster tiers, two paired runs improved the 120-position reversing zoom from **90/120** complete views to **120/120**, while pan stayed **60/60**. Preparing before pan also kept pan at 60/60 in two runs. At UltraWide size with the new raster tiers and conservative tier-boundary projections, two 4-second preparations improved the icon zoom from **28–48/120** complete views to **106/120**, with pan at **60/60** in both modes. An 8-second preparation still left the same 14 highest-zoom positions uncovered. On the 3,887-node workbook, a 4-second preparation improved zoom from **28/120** to **74/120**, with pan at **60/60**. These are atlas-coverage counts, not displayed-frame counts: the editor uses its existing canvas when a view is incomplete. The uncovered high-zoom and workbook states, effect-edit refinement time, and unpaired memory measurements keep the GPU bridge experimental.

The bridge cannot become the default until zoom coverage, effect-edit latency, pixel fidelity, visible-window presentation, resize/device-loss behavior, and paired memory tests pass. The measured first full view also does not establish an instant sharp image at document open.

### Latest editor-atlas stress pass

The feature-gated editor bridge now uses 768-pixel tiles with 128 pixels of bleed, a separate four-worker idle-prefetch queue, and single-pass CPU tile rendering. The atlas prefers to retain the lowest-zoom viewport it has seen; comparing raster tiers alone was insufficient because several camera scales share one tier. This preference is a bounded eviction hint, not a guarantee when the atlas fills. The current bridge allocates 198 slots for a 1266×1660-pixel viewport and 240 for UltraWide. Those fixed RGBA8 arrays alone reserve about **792 MiB** and **960 MiB**, respectively, before output textures and CPU render buffers. The older **471 MiB** figure above belongs to an earlier standalone prototype and must not be used as the memory cost of this editor bridge. One post-change editor process showed a roughly **4.5 GiB** physical footprint; that run was not a paired memory comparison, and the macOS session was locked during its control trace, so its apparent interaction timings are invalid as visible-frame evidence.

The same 60-position pan and 120-position reversing zoom trace at 75 Hz produced:

| Saved document and viewport | Slots | Pan covered | Zoom covered | Observation |
| --- | ---: | ---: | ---: | --- |
| 3,887-node workbook, 1266×1660 | 128 | 60/60 | 76/120 | Evicted low-zoom tiles on the return trip. |
| Workbook, 1266×1660 | 198 | 60/60 | 120/120, 119/120, 120/120 | Three repeats with four idle workers and lowest-scale retention. One tier transition still missed. |
| Lizard icon, 4300×2020 | 240 | 60/60 | 106/120 | Fourteen consecutive misses at 3.24–4× zoom, even after eight seconds of preparation. |
| Workbook, 4300×2020 | 240 | 60/60 | 78/120 | Misses at several zoom-tier transitions and on the return trip. |

The benchmark counts resident-tile coverage, not display frames. During a miss, the editor still uses its existing canvas, which can show the soft or stale image reported by the user. Prefetching the highest tier first reduced the UltraWide icon to **28/120** covered positions. Changing the tier ratio from 2× to 1.5× reduced it to **66/120**; that change was reverted. The uncovered high-zoom states are a CPU tile-production bottleneck, and neither more fixed slots nor longer idle preparation solved them in this corpus. The experimental bridge remains off by default. A real sharp GPU vector/effect path or a faster faithful CPU tile path, followed by unlocked-screen display timing and effect-edit tests, is still needed before promotion.

An isolated `/usr/bin/time -l` run of the 1266×1660 workbook trace, after the full CI run finished, measured **2,147,128,192 bytes** peak physical footprint with 198 slots and **2,426,557,632 bytes** with 240 slots. Both happened to cover 120/120 zoom positions in those individual runs. These are whole-process peaks on separate runs, not a controlled editor-memory comparison; the 240-slot increase did not demonstrate a coverage benefit for this viewport. `cargo xtask ci` passed after the latest atlas changes.

### Direct Vello GPU path (October 29)

Historical result: the Vello scene and blur code moved to `lizard-canvas-gpu`. The experiment flags and the corresponding legacy benchmark binaries have since been removed; supported content now uses the GPU path by default, with a CPU fallback only when the content requires it.

On `assets/app-icon/Lizard-new-icon.lizard`, a 1266×1720 viewport, 60 pan and 120 reversing-zoom camera positions, and a GPU fence after each frame, the first direct run measured pan p95 **23.53 ms**, zoom p95 **44.49 ms**, and **74/120** zoom frames above the 75 Hz 13.33 ms budget. Removing all effects from the benchmark document brought zoom p95 to **7.70 ms**, with no frame above budget. The icon has one large layer blur, one drop shadow, and one inner shadow; all 180 views trigger the conservative unsupported-effects guard. Removing only the layer blur reduced zoom p95 to **12.98 ms** in one run, but individual runs showed substantial variation under GPU load.

The static-effect prototype prepares one texture for each of those three effects. Early runs during concurrent compilation measured zoom p95 up to **34.72 ms** and setup as high as **512 ms**. Five quiet, sequential 1266×1720 runs with all three caches instead measured pan p95 **4.38–7.92 ms**, zoom p95 **8.03–9.85 ms**, and **0/600** zoom positions above the 75 Hz 13.33 ms budget. Five uncached runs under the same quiet conditions measured zoom p95 **17.43–18.69 ms** and **171/600** positions over budget. Three 4300×2020 cached runs measured pan p95 **5.03–5.31 ms**, zoom p95 **12.28–13.61 ms**, and **19/360** zoom positions over budget. The uncached Vello route failed at this viewport with `IntermediateTexture(TooLarge { width: 4108, height: 2248, max_width: 4096, ... })`; the cache avoids that filter-intermediate limit on this document. Cache setup in the quiet runs was **82–101 ms** after GPU initialization. These are fenced, standalone timings rather than editor presentation measurements; their sharp dependence on concurrent load and the remaining UltraWide misses require live-window validation before a default switch.

At a fixed 2× camera, the cached direct GPU render differed from the faithful CPU reference by **1.25–1.28/255 mean absolute RGB value**, with **0.27–0.33%** of pixels differing by more than 8/255 per channel. The uncached Vello-filter render differed by **3.35–3.43/255** and roughly **3%** above 8/255. At 4×, the inspected GPU and CPU snapshots looked close; RGB mean absolute error was **2.40–2.44/255** and fewer than **0.04%** of pixels differed by more than 8/255 per channel. Two cameras do not establish full document/effect parity. The static effect textures are currently rebuilt synchronously when the document changes. The renderer therefore retains `tiny-skia` for unsupported interactive content and faithful exports. The transitive `vello_cpu 0.1` uses `vello_common 0.1`, whereas this GPU scene uses `vello_common 0.3`; it is not a drop-in fallback for this scene or for Lizard's complete effect set.

The release editor was opened with the experimental feature compiled in, direct mode forced for this unsupported icon, and all three effect caches confirmed by its log. The 2880×1800 window screenshot showed the complete icon, including after a pan and zoom control trace. With the window confirmed frontmost, 60 pan and 60 wheel-zoom control requests at 75 Hz measured pan response median/p95 **13.34/17.79 ms** and zoom **13.46/15.69 ms**, with no response above 50 ms. These timings include event-queue scheduling and are not display-photon measurements. The UI's existing CPU render worker was still running redundantly in that build (`ui.inspect` reported a two-second CPU refinement); a follow-up change now skips new CPU work whenever the GPU backend returns a current texture. That change still needs the release-window rerun before its benefit can be counted.

The release-window rerun with the CPU scheduling fix opened the same 2880×1800 window, confirmed the direct GPU route and all three effect textures in the log, and showed the complete icon after pan and zoom. Two consecutive 60-pan/60-zoom traces at 75 Hz measured pan response median/p95 **13.41/17.96 ms** and **13.30/14.02 ms**, and zoom **12.89/16.67 ms** and **13.29/14.19 ms**. No control response exceeded 50 ms. The `ui.inspect` CPU render counters remained unchanged across both traces (`renderWork=full`, `uploadPixels=3,010,971`, `refineLatencyMs=267.55`), which supports that navigation did not schedule further CPU renders in this run. One initial CPU frame still occurred before the GPU texture became available. These control timings cannot establish display-photon latency, and this run does not show a consistent timing improvement over the earlier direct build. The workspace CI gate, the vector-region fallback regression test, GPU-crate Clippy, and the standalone benchmark's all-target check passed. The direct Vello path still needs broader document parity and live frame timing before becoming the default.

On October 29, maximizing the window exposed a resize regression: after the CPU worker was skipped, `visible_view` stayed at the old canvas dimensions and egui stretched the old GPU texture across the new canvas. The visible camera is now updated before the GPU backend is queried, independently of CPU work. A release-window test widened the canvas by collapsing the left sidebar; the GPU recreated its target from **1266×1660** to **2207×1660**, and screenshots before and after retained the icon's square proportions. A focused viewport-size regression test passed. The direct scene also gained per-region vector fills. A three-face GPU/CPU comparison sampled red, blue, and explicitly empty faces and matched all three RGBA pixels exactly; the capability guard still routes unsupported region paints to the faithful renderer. This does not establish parity for every vector network.

The generic Vello GPU drop-shadow filter was also compared on an isolated, opaque irregular vector with a 16-unit blur, a 5×9-unit offset, and 50% shadow alpha. At 256×256, the GPU/CPU mean absolute RGB difference was **0.205/255**, with **0.278%** of pixels differing by more than 8/255. With positive spread 3, the corresponding figures were **0.232/255** and **0.388%**; the direct route now accepts this small-spread case. At spread 10, error rose to **0.501/255** and **1.390%** above 8/255; at spread 32, it reached **3.214/255** and **10.165%**. A 50%-opaque fill diverged by **8.934/255** on average and **24.149%** above 8/255. Those cases, strokes, and stacked effects retain the fallback. This is one fixture, so broader shadow parity remains open.

A parallel probe of `vello_cpu 0.3` on the same fixture measured **0.323/255** mean error for zero spread and **0.363/255** for spread 3; both were slightly farther from the existing renderer than `vello_gpu 0.3`. It therefore provides no measured fidelity reason to replace the current export renderer yet. The icon's direct cached GPU path was also compared at 512×512: fit/detail views differed by **0.649/255** and **1.584/255** mean RGBA value, respectively, from the CPU reference. The second view had **0.118%** of pixels above 16/255. These comparisons are useful migration baselines, not proof of all-effect parity.

An inverse-mask Vello filter was also tried for an arbitrary vector's inner shadow. It matched only at zero blur; at radius 16 it differed by **2.071/255** mean RGB value and **8.706%** of channels above 8/255. That implementation was discarded, so arbitrary vector inner shadows remain on the faithful route. Separately, resizing a 256×256 GPU target to 320×256 and rerendering the shadow fixture reduced its mean RGB difference from **0.205/255** to **0.164/255**, indicating that the new target retained correct geometry and color after the size change.

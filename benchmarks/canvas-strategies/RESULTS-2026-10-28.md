# Canvas prototype measurements — 2026-10-28

## Scope and method

These measurements used an Apple M1 with 16 GiB unified memory and a 5120 × 2160, 75 Hz display. The saved `benchmarks/canvas-strategies/fixtures/ultrawide-workbook.figcraft` fixture has 3,887 nodes and 77 frames. Both programs used release builds. The prototype used a 5120 × 2160 offscreen canvas and a 5120 × 2100 Metal window; the current editor, with panels hidden, had a 5120 × 2020 physical-pixel canvas. The prototype generated camera positions inside its winit loop; the editor received the same 120 positions through its JSON control channel. This is a useful workload comparison, **not** a controlled display-latency or FPS comparison.

The camera trace contains 60 pan positions and 60 continuous zoom positions, scheduled at 75 Hz. `--trace-repeats=10` exercises 1,200 positions; `--trace-repeats=60` exercises 7,200. Times marked “first visual” stop when the frame is submitted to Metal, not when the display emits light. `present_call_ms` and queue completion are distinct timings; neither proves that pixels were displayed within that interval. Run-to-run values change with window focus and system load. Occluded Metal-window runs were discarded.

## Memory: the 471 MiB atlas

The 240-slot, fixed-size atlas is **471.3 MiB**, about **2.9%** of this Mac's 16 GiB. It is one GPU allocation, not the memory of the whole program. macOS's peak memory footprint includes considerably more than the process's maximum resident set size (RSS), so the footprint is the more conservative comparison for this unified-memory machine.

| Release process and workload | Atlas | Max RSS | Peak memory footprint |
| --- | ---: | ---: | ---: |
| GPU prototype, 10 traces, fidelity fallback for drop shadows | 471.3 MiB | 348 MiB | 1,104 MiB |
| GPU prototype, 10 traces, same fallback including preview | 471.3 MiB | 333 MiB | 1,093 MiB |
| GPU prototype, one verified trace, same fallback | 471.3 MiB | 407 MiB | 1,212 MiB |
| GPU prototype, 60 traces, same fallback | 471.3 MiB | 343 MiB | 1,091 MiB |
| GPU prototype, 10 traces, earlier GPU shadow path | 471.3 MiB | 359–362 MiB | 1,232–1,233 MiB |
| Current editor, extended comparison session including 10-trace runs, full app | Separate dynamic cache | 917 MiB | 1,469 MiB |

The current editor figures include its full interface and control server; the prototype is a separate renderer window. They are not identical application workloads. The prototype's fixed atlas did not grow with repeated pan and zoom. This Mac showed roughly half its memory available during the measured runs and no swap activity in the timed processes. The data does **not** justify imposing an arbitrary 256 MiB atlas target. A useful next check is an 8 GiB Mac or deliberate memory pressure with several documents open, then an adaptive budget if pressure or eviction costs warrant it.

## Effect fidelity

A controlled 512 × 512 scene compared the direct GPU output with the document renderer, using the fraction of pixels that differ by more than 4/255 in any RGBA channel. It is one representative scene per effect, not exhaustive parity.

| Effect | Direct GPU difference from CPU | Current prototype route |
| --- | ---: | --- |
| None | 0.072% | GPU |
| Drop shadow | **24.327%**; the shadow was visibly absent | CPU tile and preview fallback |
| Inner shadow | 2.943% | CPU fallback |
| Layer blur | 0.003% | GPU |
| Background blur | 0.072% | GPU |
| Noise | 13.096% | CPU fallback |
| Texture | 1.322% | CPU fallback |
| Glass | 2.314% | CPU fallback |

With the drop-shadow tile fallback, the whole workbook differed from the CPU reference on **0.065%** of base-view pixels and **0.693%** of zoomed-view pixels; the earlier direct GPU path differed on **0.891%** and **0.914%**, respectively. Full tile preparation rose from roughly 5.3 s in clean ten-trace runs to 8.6–9.1 s with the fallback. This is a fidelity-versus-preparation-cost tradeoff, and the prototype still needs more effect combinations, masks, fonts, images, color profiles, and blend modes tested before it becomes the default renderer.

## Edit latency

The current editor's JSON command acknowledgement is not the same as a refined canvas frame. With the same fixture and a release build, five text-property edits refined in **93–167 ms**; creating a rectangle took **588 ms** to refine; adding a drop shadow took **175 ms**; four actual shadow radius edits refined in **149–169 ms**. The prototype's isolated GPU rectangle-fill patch took **25–35 ms** for four dirty tiles, plus **0.9–3.6 ms** to compose. That isolated patch does not include the editor UI, text shaping, effect invalidation, or a display flip. It cannot be used as an in-app edit-latency claim for the prototype.

## Readiness to make this the default canvas

### Follow-up: scheduling, capacity, and corpus checks

The 240-slot atlas was tested against smaller fixed budgets on the same three-trace warm-interaction workload. Capacity 160/200/220/230 produced 332/188/102/52 frames with missing base tiles out of 360; 240 produced **zero**. The 471.3 MiB atlas is therefore justified for this particular UltraWide trace. It is not a universal minimum for smaller displays. The full prototype's measured peak memory footprint varied from roughly 1.12 to 1.41 GiB across these runs; the atlas alone is not its process memory.

The worker previously held the GPU presentation mutex during CPU effect rasterization. Moving that rasterization outside the lock reduced one early-interaction run's median pan and zoom `present()` calls from 2.51/13.27 ms to 0.99/1.02 ms. A four-worker asynchronous CPU queue reduced full preparation in one run from 7.08 s (four-worker batches) to 3.87–4.36 s, depending on warm ordering and system load. These are short, unpaired runs; they establish that the worker structure matters, not a stable speedup percentage.

With four asynchronous workers and **after preparation**, a verified 120-position trace had no missing base tiles or stale detail. Its base and detail image differences from the CPU renderer were 0.065% and 0.693% of pixels above 4/255. Median/p95 `present()` call times were 3.16/6.75 ms for pan and 3.25/6.43 ms for zoom. The first visual was submitted at 0.94 s, complete preparation at 3.89 s, and peak memory footprint was 1.41 GiB. None of these are display-photon timestamps.

**Early interaction still fails the quality target.** When the trace starts after the initial visible base and detail tiles but while pan coverage is still preparing, 55 of 349 presented pan/zoom states in one run lacked at least one base tile, even after retaining completed tiles that had briefly moved outside the camera's prefetch region. Starting only after all base tiles hides that failure but delays the simulated interaction until preparation is complete. The current 512-pixel overview is visibly soft on a 5120-pixel canvas during that period. A full-width direct Vello render also hit its 4096-pixel intermediate-texture limit. Splitting the viewport into two 2560-pixel strips took 133 + 40 ms on the first direct-GPU render and still omitted unsupported effects. This is not a suitable sharp fallback yet.

The pixel corpus now covers 66 views from the example documents and the saved Lizard icon file. Eighteen views qualified for direct GPU rendering; their worst difference was 3.562% of pixels above 4/255 (1.403% average). The other 48 need a faithful fallback for at least one unsupported feature; their direct output was deliberately not treated as parity evidence. The icon contains both drop and inner shadows, so it remains on the CPU route. The complex workbook routes 99/160 planned base tiles and 59/78 detail tiles through that route.

The analytic rounded-rectangle shadow now renders on the GPU with a cutout for shadows hidden behind the shape. In a 72-case radius/spread/opacity/zoom sweep, the supported low-opacity subset's worst difference was 4.261% of pixels above 4/255. A clipped opaque frame with a child differed by 1.555%; an unclipped frame whose child stayed inside the rounded outline differed by 1.310%. Higher-opacity shadows diverged by as much as 39.254% in the direct experiment and remain on the CPU route. Only 20 of the workbook's 172 shadows currently qualify for the analytic path. The parity sweep is an executable gate, not a claim of support for arbitrary shadow shapes or blends.

These follow-up measurements strengthen the post-preparation case, while the early-pan failure, unsupported effects, real display timing, and in-editor edit/device tests still prevent making this the default renderer.

The prototype establishes a promising bounded GPU cache and, after preparation, covers the tested pan and zoom trace without missing base tiles. It does **not** yet prove default-renderer readiness. The outstanding evidence is:

1. Pixel parity over representative documents and effect combinations, including a faithful fast drop-shadow path rather than a costly CPU tile fallback.
2. A sharp and faithful initial preview, with measured time to first correct frame and early zoom behavior. The 28 stale-detail frames in the early trace exceed the desired 50 ms visual budget if they are visible to the user.
3. A single input and display-timestamp harness for both renderers, with the same canvas dimensions, to measure actual visible frame age and worst-case latency rather than `present()` or control-channel counters.
4. Integration behind a selectable editor backend, then real text, image, effect, pan, zoom, resize, document-switch, and device-loss tests. The isolated prototype cannot validate those editor interactions.
5. Sustained memory-pressure and lower-memory-device runs, plus native and WASM regression gates after integration.

The 471 MiB atlas is a reasonable measured starting point on this 16 GiB UltraWide Mac. The decision to change it should come from memory pressure, competing documents, and eviction costs, not a smaller round number.

### Reproducible random motion and cache eviction follow-up

The smooth sinusoidal trace did not expose a cache correctness bug. A new seeded `--trace=random` simulates 60 pointer-like pan samples followed by 60 quick, reversing scroll samples; the same 120 camera positions repeat so runs can be compared. At 75 Hz, three repeats request 360 positions. This is still synthetic input inside the prototype, not OS mouse and display timing.

The worker's `rendered` set originally rejected every later request for a tile it had ever produced. Once the bounded atlas evicted that tile, zoom could never restore it. A regression test now checks that a live request re-renders an evicted tile, while planned warm-up work remains deduplicated. In a three-repeat random run with a 240-slot atlas, this correction reduced stale zoom-detail frames from **155 to 49**. It did not eliminate them.

Warm-up region jobs are now submitted on demand, with live requests taking priority over planned work. In two alternating, three-repeat random comparisons, 2×2 regions finished preparation in 3.39/3.75 s versus 3.63/3.88 s for individual tiles, and peak memory footprint was 1.18 GiB versus 1.33/1.36 GiB. Presentation p95 varied across runs; these pairs do **not** establish a repeatable improvement in presentation latency. Both routes still had about 153–156 stale detail frames before the eviction fix. The compact region also passed a separate tile-pixel comparison against individual faithful renders.

An atlas with 255 total slots is the largest single texture-array allocation this GPU accepts when one slot is reserved for the preview: Metal reports a 256-layer limit. A 280-slot experiment previously aborted during texture creation; the prototype now checks the device limit and returns an error. The 255-slot atlas with 95 detail slots uses 500.6 MiB, about 3.1% of this 16 GiB machine. With the eviction fix, the random-trace sweep gave:

| 2×2 CPU regions in flight | Full preparation | Stale detail frames / ~180 zoom frames | Longest stale sequence | Peak process footprint |
| ---: | ---: | ---: | ---: | ---: |
| 1 | 5.33 s | 14 | 187 ms | 1.15 GiB |
| 2 | 3.88 s | **10** | **133 ms** | 1.23 GiB |
| 3 | 3.39 s | 20 | 267 ms | 1.21 GiB |
| 4 | 4.24 s | 23 | 307 ms | 1.21 GiB |

Each row is one release run with the window frontmost. The best observed setting still exceeded the requested 50 ms visible-quality limit; these are scheduled-frame streaks and do not claim display-photon duration. The first-preview interaction run at the best setting was worse: first visual submitted at 0.62 s, initial visible tiles at 3.01 s, and all warm tiles at 4.58 s. All 95 presented interaction frames had missing base tiles; the longest uninterrupted missing-base sequence was at least 1.27 s, and the longest stale-detail sequence was 0.68 s. The overview remained lower resolution while the detailed tiles were prepared. The prototype therefore remains a **no-go** as the default renderer, even though the post-preparation cache and memory results are promising.

A separate `--verify` run with the 255-slot/two-region configuration completed after an event-loop watchdog fix. Its random-trace base and zoom reference images differed on 2.113% and 1.229% of pixels by more than 4/255. The 120-position trace had zero missing base frames, but 11 stale-detail frames and a 147 ms longest stale sequence. The earlier run without the watchdog reached the image comparison and then waited indefinitely for a redraw; it was discarded rather than treated as a timing sample.

The next implementation gate is a sharp, effect-faithful path for uncovered areas during *early* pan and zoom. More atlas memory alone cannot solve the 1.27 s preview-phase gap. After that path exists, rerun the random and sinusoidal traces inside the actual editor with pointer events, display timestamps or frame capture, edit invalidation, device loss, native/WASM builds, and memory pressure. A fast `present()` call is insufficient evidence by itself.

### Sharp-preview feasibility probe

A full-resolution CPU geometry pass with effects omitted took 22.77 ms for the 5120 × 2160 workbook view, versus 503.15 ms for its full effect render, in one release run. Blending that sharp pass over a five-times-smaller effect preview reduced workbook pixels differing from the faithful image by more than 4/255 from 7.101% to 1.439%. The same method **failed** on the saved Lizard icon: a 1024 × 1024 geometry pass took 3.17 ms, but the hybrid raised the >4/255 difference from 5.723% to 11.968%. Visual inspection showed that opaque geometry covered the icon's inner shadow and softened surface treatment. This shortcut cannot be adopted as the fidelity solution. The probe and its PNG comparisons are in `geometry_overlay_parity.rs` and the ignored benchmark output directory.

The working-tree `cargo xtask ci` gate passed after fixing a timing-sensitive zoom-preview assertion: it had previously accepted an idle worker before the requested zoom's image reached the canvas. The benchmark package's release tests, controlled shadow and region parity probes, corpus parity run, and `cargo clippy --all-targets -- -D warnings` also passed. The benchmark package is separate from the shipping workspace, so this does not substitute for integration tests of a new editor backend.

## Reproduce

```sh
CARGO_TARGET_DIR=target/canvas-strategies/target cargo run --release \
  --manifest-path benchmarks/canvas-strategies/Cargo.toml \
  --bin streaming_window -- --slots=240 --background-warm --verify

/usr/bin/time -l target/canvas-strategies/target/release/streaming_window \
  --slots=240 --background-warm --trace-repeats=10

CARGO_TARGET_DIR=target/canvas-strategies/target cargo run --release \
  --manifest-path benchmarks/canvas-strategies/Cargo.toml --bin effect_parity
```

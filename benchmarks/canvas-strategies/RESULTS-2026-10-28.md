# Canvas prototype measurements — 2026-10-28

## Scope and method

These measurements used an Apple M1 with 16 GiB unified memory and a 5120 × 2160, 75 Hz display. The saved `examples/ultrawide-workbook.figcraft` fixture has 3,887 nodes and 77 frames. Both programs used release builds. The prototype used a 5120 × 2160 offscreen canvas and a 5120 × 2100 Metal window; the current editor, with panels hidden, had a 5120 × 2020 physical-pixel canvas. The prototype generated camera positions inside its winit loop; the editor received the same 120 positions through its JSON control channel. This is a useful workload comparison, **not** a controlled display-latency or FPS comparison.

The camera trace contains 60 pan positions and 60 continuous zoom positions, scheduled at 75 Hz. `--trace-repeats=10` exercises 1,200 positions; `--trace-repeats=60` exercises 7,200. Times marked “first visual” stop when the frame is submitted to Metal, not when the display emits light. `present_call_ms` and queue completion are distinct timings; neither proves that pixels were displayed within that interval. Run-to-run values change with window focus and system load. Occluded Metal-window runs were discarded.

## Memory: the 471 MiB atlas

The 240-slot, fixed-size atlas is **471.3 MiB**, about **2.9%** of this Mac's 16 GiB. It is one GPU allocation, not the memory of the whole program. macOS's peak memory footprint includes considerably more than the process's maximum resident set size (RSS), so the footprint is the more conservative comparison for this unified-memory machine.

| Release process and workload | Atlas | Max RSS | Peak memory footprint |
| --- | ---: | ---: | ---: |
| GPU prototype, 10 traces, fidelity fallback for drop shadows | 471.3 MiB | 348 MiB | 1,104 MiB |
| GPU prototype, 10 traces, same fallback including preview | 471.3 MiB | 333 MiB | 1,093 MiB |
| GPU prototype, one verified trace, same fallback | 471.3 MiB | 407 MiB | 1,212 MiB |
| GPU prototype, 60 traces, same fallback | 471.3 MiB | 343 MiB | 1,091 MiB |
| GPU prototype, 10 traces, earlier GPU shadow path | 471.3 MiB | 359–362 MiB | 1,232–1,233 MiB |
| Current editor, extended comparison session including 10-trace runs, full app | Separate dynamic cache | 917 MiB | 1,469 MiB |

The current editor figures include its full interface and control server; the prototype is a separate renderer window. They are not identical application workloads. The prototype's fixed atlas did not grow with repeated pan and zoom. This Mac showed roughly half its memory available during the measured runs and no swap activity in the timed processes. The data does **not** justify imposing an arbitrary 256 MiB atlas target. A useful next check is an 8 GiB Mac or deliberate memory pressure with several documents open, then an adaptive budget if pressure or eviction costs warrant it.

| One trace starting during preparation | 0.99 s | 9.36 s | 119/120 presented; 1 coalesced | 0 | 28 | 31.73 ms / 0 |

The initial preview is lower resolution than the final tiles. In the older rows it used the direct GPU path, which omitted drop shadows until tiles replaced it. The newer ten-trace run logged `preview path=cpu_fidelity render_submit_ms=36.48`; its first visual was submitted at 0.77 s and full preparation finished at 8.49 s. This controlled change did not show a startup regression, but it does not make the initial preview sharp at the display's native resolution.

In the current editor, the valid ten-trace run drew 63–75 UI frames for each set of 120 control requests; the prototype's internal trace presented 1,196 of 1,200 states in the row above. These counters use different input and presentation paths. The earlier same-fixture editor inspection saw a stale zoom texture for about 226–328 ms. The new run did not capture display timestamps or pixel maps of the editor's blurred pan strips, so it cannot rank perceived sharpness precisely.

## Effect fidelity

A controlled 512 × 512 scene compared the direct GPU output with the document renderer, using the fraction of pixels that differ by more than 4/255 in any RGBA channel. It is one representative scene per effect, not exhaustive parity.

| Effect | Direct GPU difference from CPU | Current prototype route |
| --- | ---: | --- |
| None | 0.072% | GPU |
| Drop shadow | **24.327%**; the shadow was visibly absent | CPU tile and preview fallback |
| Inner shadow | 2.943% | CPU fallback |
| Layer blur | 0.003% | GPU |
| Background blur | 0.072% | GPU |
| Noise | 13.096% | CPU fallback |
| Texture | 1.322% | CPU fallback |
| Glass | 2.314% | CPU fallback |

With the drop-shadow tile fallback, the whole workbook differed from the CPU reference on **0.065%** of base-view pixels and **0.693%** of zoomed-view pixels; the earlier direct GPU path differed on **0.891%** and **0.914%**, respectively. Full tile preparation rose from roughly 5.3 s in clean ten-trace runs to 8.6–9.1 s with the fallback. This is a fidelity-versus-preparation-cost tradeoff, and the prototype still needs more effect combinations, masks, fonts, images, color profiles, and blend modes tested before it becomes the default renderer.

## Edit latency

The current editor's JSON command acknowledgement is not the same as a refined canvas frame. With the same fixture and a release build, five text-property edits refined in **93–167 ms**; creating a rectangle took **588 ms** to refine; adding a drop shadow took **175 ms**; four actual shadow radius edits refined in **149–169 ms**. The prototype's isolated GPU rectangle-fill patch took **25–35 ms** for four dirty tiles, plus **0.9–3.6 ms** to compose. That isolated patch does not include the editor UI, text shaping, effect invalidation, or a display flip. It cannot be used as an in-app edit-latency claim for the prototype.

## Readiness to make this the default canvas

The prototype establishes a promising bounded GPU cache and, after preparation, covers the tested pan and zoom trace without missing base tiles. It does **not** yet prove default-renderer readiness. The outstanding evidence is:

1. Pixel parity over representative documents and effect combinations, including a faithful fast drop-shadow path rather than a costly CPU tile fallback.
2. A sharp and faithful initial preview, with measured time to first correct frame and early zoom behavior. The 28 stale-detail frames in the early trace exceed the desired 50 ms visual budget if they are visible to the user.
3. A single input and display-timestamp harness for both renderers, with the same canvas dimensions, to measure actual visible frame age and worst-case latency rather than `present()` or control-channel counters.
4. Integration behind a selectable editor backend, then real text, image, effect, pan, zoom, resize, document-switch, and device-loss tests. The isolated prototype cannot validate those editor interactions.
5. Sustained memory-pressure and lower-memory-device runs, plus native and WASM regression gates after integration.

The 471 MiB atlas is a reasonable measured starting point on this 16 GiB UltraWide Mac. The decision to change it should come from memory pressure, competing documents, and eviction costs, not a smaller round number.

## Reproduce

```sh
CARGO_TARGET_DIR=target/canvas-strategies/target cargo run --release \
  --manifest-path benchmarks/canvas-strategies/Cargo.toml \
  --bin streaming_window -- --slots=240 --background-warm --verify

/usr/bin/time -l target/canvas-strategies/target/release/streaming_window \
  --slots=240 --background-warm --trace-repeats=10

CARGO_TARGET_DIR=target/canvas-strategies/target cargo run --release \
  --manifest-path benchmarks/canvas-strategies/Cargo.toml --bin effect_parity
```

Raw local outputs are in the ignored `target/canvas-strategies/` directory: `drop-shadow-fallback-verify.log`, `drop-shadow-fallback-10runs.log`, `drop-shadow-fallback-early.log`, `gpu-60runs-memory.log`, `gpu-faithful-preview-verify.log`, `gpu-faithful-preview-10runs.log`, `memory-gpu-10runs-clean-{1,2}.log`, `memory-editor-1.log`, `editor-memory-10runs.json`, `editor-edit-latencies.json`, `edit-gpu-current.log`, and `effect-parity-artifacts.log`.
